Q1. 프로세스 vs 스레드

프로세스와 스레드의 차이는? 실제로 코드를 실행하는 주체는?
핵심 명제: 프로세스는 게으르다(inert). 실제로 실행하는 것은 항상 스레드다.
구분프로세스스레드
역할자원의 컨테이너실행의 주체
소유물가상 주소 공간, 커널 핸들 테이블, 코드/데이터/DLL스택, 레지스터 상태(Context)
비유공장 건물공장 노동자

중요 명제

  • 모든 프로세스는 최소 하나의 스레드를 가진다 (Primary Thread)
  • 프로세스의 모든 스레드가 종료되면 프로세스도 종료된다
  • 스레드는 프로세스의 자원(주소 공간, 핸들)을 공유한다 → 통신은 쉽지만 동기화가 필요

Q2. 스레드 생성 시 OS가 할당하는 두 가지

스레드를 만들 때 OS가 반드시 생성하는 두 가지는?
요소위치용도
Thread Kernel Object 커널 영역 OS가 스레드를 관리하기 위한 자료구조
(CONTEXT, ID, 종료 코드, 시그널 상태, 사용 카운터 포함)
Thread Stack 프로세스 주소 공간 (유저 영역) 함수 호출, 지역 변수 저장
기본 크기: 1MB
💡 게임 프로그래머 관점: 스레드 1000개 만들면 스택만 1GB. 그래서 Thread Pool 패턴을 사용. CONTEXT 복원/저장이 컨텍스트 스위칭 비용.
⚠️ TLS는 정답이 아님: TLS는 선택적(optional)이고 명시적 할당이 필요. 모든 스레드가 자동으로 받는 것은 스택.

Q3. CreateThread의 매개변수 6개

HANDLE WINAPI CreateThread(
    LPSECURITY_ATTRIBUTES   lpThreadAttributes,  // 1: 보안 (보통 NULL)
    SIZE_T                  dwStackSize,         // 2: 스택 크기 (보통 0 = 1MB)
    LPTHREAD_START_ROUTINE  lpStartAddress,      // 3: 스레드 함수 포인터 ⭐
    LPVOID                  lpParameter,         // 4: 함수 인자 (void*) ⭐
    DWORD                   dwCreationFlags,     // 5: 0 또는 CREATE_SUSPENDED
    LPDWORD                 lpThreadId           // 6: 스레드 ID 출력 (보통 NULL)
);

매개변수별 핵심

#이름요점
1lpThreadAttributes거의 항상 NULL (기본 보안)
2dwStackSize거의 항상 0 (EXE 헤더 기본값 1MB)
3lpStartAddress스레드 함수 포인터. 시그니처는 DWORD WINAPI Func(LPVOID)
4lpParameter함수에 전달할 데이터. void* 하나만 가능
5dwCreationFlags0 또는 CREATE_SUSPENDED (실행 보류)
6lpThreadId거의 항상 NULL

매개변수가 1개뿐인 이유와 해결책

LPVOID 1개만 가능하지만, void*이므로 구조체 포인터로 묶어 넘기면 사실상 무제한. 
struct ThreadParams {
    int id;
    const char* name;
    float speed;
};

DWORD WINAPI MyThreadFunc(LPVOID lpParam) {
    ThreadParams* p = (ThreadParams*)lpParam;  // 캐스팅
    // ... 사용 ...
    delete p;  // ⚠️ 동적 할당 시 해제 책임
    return 0;
}

CREATE_SUSPENDED 활용 (게임 프로그래머 필수)

HANDLE h = CreateThread(NULL, 0, ThreadFunc, param,
                          CREATE_SUSPENDED, NULL);  // 일시 정지로 생성
SetThreadPriority(h, THREAD_PRIORITY_HIGHEST);  // 우선순위 설정
SetThreadAffinityMask(h, 0x01);                // 코어 친화성 설정
ResumeThread(h);                                // 이제 실행 시작

Q4. 스레드 함수 작성 가이드라인 5가지

ThreadFunc를 작성할 때 반드시 지켜야 할 5가지는?
#가이드라인위반 시 결과
1 DWORD WINAPI Func(LPVOID) 시그니처 준수 호출 규약 불일치로 스택 오염 → 크래시
2 전역/정적 변수 사용 최소화 여러 스레드가 공유 → 데이터 경쟁
3 LPVOID 캐스팅으로 매개변수 사용 타입 안전성 직접 책임
4 예외는 스레드 함수 내에서 처리 처리 안 하면 프로세스 전체 종료
5 CRT 사용 시 _beginthreadex 권장 CRT 스레드별 데이터 누수

올바른 스레드 함수 예시

DWORD WINAPI ThreadFunc(LPVOID lpParam) {
    try {
        Params* p = (Params*)lpParam;  // 3. 캐스팅
        int localData = p->value;     // 2. 지역 변수 우선
        DoWork(localData);
    }
    catch (std::exception& e) {     // 4. 예외 처리
        return 1;
    }
    return 0;
}

Q5. 스레드 종료 방법 4가지

#방법평가설명
1 스레드 함수 return 권장 모든 자원이 정상 정리되는 유일한 방법
2 ExitThread() 비권장 C++ 객체 소멸자 호출 안 됨 (자살)
3 TerminateThread() 절대 금지 스택 미해제, 데드락 가능 (타살)
4 프로세스 종료 비권장 모든 스레드 강제 종료
🚫 TerminateThread가 절대 금지인 이유:
  • C++ 객체 소멸자가 호출되지 않음 (가장 큰 문제)
  • DLL_THREAD_DETACH 통지 없음
  • 임계 영역(Critical Section) 안에서 죽으면 락이 영원히 잠김 → 데드락
  • 비동기 함수 — 진짜 종료됐는지 보장 못 함
  • (구버전 Windows / 리처 책 시점) 스택 메모리도 해제 안 됨 — 모던 Windows에선 OS가 해제하지만, 위 문제들은 여전함
📌 가장 위험한 것은 메모리 누수가 아니라 데드락: 스레드가 락을 쥔 상태에서 TerminateThread 당하면 그 락은 영원히 안 풀린다. 다른 스레드들이 그 락을 기다리면서 멈춤 → 게임 멈춤.

외부에서 스레드를 어떻게 종료시키나? — 협력적 종료 패턴

std::atomic<bool> g_shouldStop = false;

DWORD WINAPI WorkerThread(LPVOID) {
    while (!g_shouldStop) {       // 매 반복마다 체크
        DoWork();
    }
    return 0;                    // 자연 종료
}

// 메인에서
g_shouldStop = true;                 // 신호만 보냄
WaitForSingleObject(h, INFINITE);    // 깔끔하게 끝날 때까지 대기
CloseHandle(h);

Q6. _beginthreadex vs CreateThread

두 함수의 차이는? 왜 _beginthreadex를 권장하나?

핵심 차이: CRT 스레드별 데이터 (_tiddata)

CRT 함수스레드별 데이터
errno에러 코드
strtok, wcstok토큰 파싱 상태
asctime, gmtime정적 버퍼
rand난수 시드

동작 차이

_beginthreadex:
  1. _tiddata 블록 할당
  2. 스레드 TLS 슬롯에 연결
  3. CreateThread 호출
  4. 스레드 종료 시 _endthreadex가 _tiddata 자동 해제 ✅
CreateThread:
  1. 스레드만 생성
  2. CRT 함수 호출 시 즉석에서 _tiddata 만듦
  3. 종료 시 _endthreadex 안 불림 → _tiddata 메모리 누수

한 줄 결론

CRT 함수를 쓴다면 항상 _beginthreadex를 써라. CreateThread는 잊어라.
참고: std::thread는 내부적으로 _beginthreadex를 사용하므로 이 문제가 자동 해결됨.

Q7. ExitThread를 C++에서 쓰면 안 되는 이유

한 줄 요약: OS 커널 자원은 정리되지만, C++ 객체 소멸자가 호출되지 않아 자원 누수 발생.

왜?

  • OS는 C++ 언어를 모름. 시스템 콜만 처리
  • 소멸자 호출은 컴파일러가 생성한 코드
  • 함수가 return으로 끝나야 컴파일러 생성 정리 코드가 실행됨
  • ExitThread는 함수 중간에 강제 점프 → 정리 코드 건너뜀
DWORD WINAPI ThreadFunc(LPVOID) {
    std::vector<int> data(10000);   // 힙 할당
    std::ofstream file("a.txt");    // 파일 핸들
    std::lock_guard lock(g_mutex);  // 뮤텍스 락

    ExitThread(0);  // 💥 여기서 점프
    // data 소멸자 X → 메모리 누수
    // file 소멸자 X → 파일 핸들 누수
    // lock 소멸자 X → 뮤텍스 영원히 잠김 (데드락!)
}

Q8. 스택 변수의 수명 함정 (Race Condition)

다음 코드의 문제점은?
DWORD WINAPI ThreadFunc(PVOID pvParam) {
    int n = *(int*)pvParam;
    printf("%d\n", n);
    return 0;
}

void StartThread() {
    int value = 42;
    CreateThread(NULL, 0, ThreadFunc, &value, 0, NULL);
}  // ← StartThread 종료, value 사라짐

핵심 원리

  1. CreateThread는 논블로킹 (non-blocking) — 즉시 반환
  2. 새 스레드 실행 시점은 OS 스케줄러가 결정 (예측 불가)
  3. value는 스택 변수 → StartThread 종료 시 사라짐
  4. ThreadFunc가 늦게 실행되면 쓰레기 값 참조
⚠️ 가장 무서운 점: 재현이 안 됨
개발/QA에선 잘 돌다가, 출시 후 사용자 PC에서 가끔 크래시. 디버깅 지옥의 전형적인 패턴.

해결책

방법 1: 힙 할당 (가장 흔함)

void StartThread() {
    int* value = new int(42);
    CreateThread(NULL, 0, ThreadFunc, value, 0, NULL);
}

DWORD WINAPI ThreadFunc(PVOID pvParam) {
    int* p = (int*)pvParam;
    printf("%d\n", *p);
    delete p;  // 스레드가 정리 책임
    return 0;
}

방법 2: 값 자체를 포인터로 전달 (작은 데이터만)

CreateThread(NULL, 0, ThreadFunc,
             (LPVOID)(intptr_t)value,  // 값을 포인터로 위장
             0, NULL);

방법 3: WaitForSingleObject로 대기

int value = 42;
HANDLE h = CreateThread(NULL, 0, ThreadFunc, &value, 0, NULL);
WaitForSingleObject(h, INFINITE);  // 끝날 때까지 value 살아있음
CloseHandle(h);
💡 게임 프로그래머 원칙: 스레드에 넘기는 데이터는 그 스레드가 끝날 때까지 살아있어야 한다. 스택 변수는 거의 항상 잘못된 선택.

Q9. 스레드 종료 시 OS의 정리 작업

스레드가 return으로 종료될 때, OS가 수행하는 작업들은?

OS가 수행하는 7가지 작업

#작업설명
1C++ 객체 소멸자 실행스택에 있는 객체들의 소멸자가 역순으로 호출
2스택 메모리 해제1MB 가상 메모리 반환 (TerminateThread는 이거 안 함)
3종료 코드 저장STILL_ACTIVE → 반환값(예: 0)으로 변경
4커널 오브젝트 시그널 상태로nonsignaled → signaled (WaitForSingleObject가 풀림)
5사용 카운트 1 감소아직 0이 아닐 수 있음 (HANDLE 참조 남아있음)
6DLL_THREAD_DETACH 통지사용 중이던 DLL들에 종료 알림
7마지막 스레드면 프로세스 종료프로세스의 모든 스레드 죽으면 프로세스도 죽음
💡 비유로 기억: "몸은 정리하지만, 이름표는 남긴다" — 스택과 자원은 즉시 정리되지만, 커널 오브젝트는 HANDLE 참조가 다 닫혀야 사라짐.

Q10. 핸들 vs 스레드의 생명주기

CloseHandle로 핸들을 닫으면 스레드는 종료되나?
답: 아니다. 핸들과 스레드는 별개의 생명주기를 가진다.

사용 카운트 추적

HANDLE h = CreateThread(...);
// 사용 카운트 = 2 (스레드 자신 + HANDLE)

CloseHandle(h);
// 사용 카운트 = 1 (HANDLE만 -1)
// 스레드는 여전히 실행 중!

// ... 스레드 함수 종료 ...
// 사용 카운트 = 0 → 커널 오브젝트 파괴

네 가지 생명주기 정리

관점생명주기
스레드 실행 자체함수 시작 ~ return/ExitThread/TerminateThread
스택 메모리스레드 실행 동안만
스레드 커널 오브젝트CreateThread ~ 마지막 핸들이 닫힐 때
HANDLECreateThread ~ CloseHandle

"Fire and forget" 패턴

// 종료 코드에 관심 없을 때 흔히 쓰는 패턴
HANDLE h = CreateThread(NULL, 0, BackgroundTask, NULL, 0, NULL);
CloseHandle(h);  // 즉시 닫음, 스레드는 백그라운드 실행
⚠️ 흔한 실수: CloseHandle 빼먹으면 커널 오브젝트가 영원히 메모리에 남음 → 핸들 누수. 게임처럼 스레드를 자주 만들면 누적됨.

보너스: Thread Pool 개념

왜 필요한가?

  • 스레드 생성/소멸 비용: 커널 오브젝트 + 1MB 스택 할당 + 컨텍스트 초기화
  • 스레드 1000개 만들면 메모리 1GB + 컨텍스트 스위칭 폭발
  • 해결: 코어 수만큼 스레드 미리 만들고, while 루프로 작업을 계속 처리

핵심 코드 (단순화)

void WorkerThread() {
    while (running) {              // ← 핵심: while 루프
        Job job = jobQueue.Pop();
        job.Execute();              // 작업 끝나도 스레드는 안 죽음
    }                                // running = false 되어야 종료
}

std::thread vs CreateThread

기능CreateThread (Win32)std::thread (C++11)
플랫폼Windows 전용크로스 플랫폼

게임 프로그래머 결론:
  • 일반 게임 코드는 std::thread
  • 엔진 코어/성능 critical 부분은 CreateThread 또는 _beginthreadex
  • std::thread의 native_handle()로 Win32 API 직접 사용 가능
  • 둘 다 알아야 함

🔧 심화: 스택 관리의 주체는 OS인가 컴파일러인가?

"스택을 정리하는 주체"는 누구인가? 두 층위로 나눠 봐야 함.

스택에는 두 가지 층위가 있다

층위관리 주체설명
1. 스택 가상 메모리 영역 (1MB) OS 커널 CreateThread 시 예약(Reserve), 종료 시 해제(Release).
VirtualAlloc/VirtualFree 메커니즘. 컴파일러는 존재조차 모름.
2. 스택 프레임 + C++ 객체 소멸자 컴파일러 함수 프롤로그/에필로그(rsp 조작), 객체 생성자/소멸자 호출 코드 삽입.
OS가 마련해준 영역 위에서 "가구를 배치"하는 셈.

호텔 비유

실제비유

TerminateThread가 문제인 진짜 이유 (정정)

#문제스킵되는 책임 영역
1C++ 객체 소멸자 호출 안 됨컴파일러가 생성한 정리 코드 스킵
2DLL_THREAD_DETACH 통지 없음OS 정리 일부 스킵
3임계 영역 락이 안 풀림 (데드락)1번의 결과
4(구버전 한정) 스택 메모리 해제 안 됨OS 정리 스킵 (모던 Windows에선 해결됨)
⚠️ 이전 노트 정정:
"TerminateThread → 스택 해제 안 됨 → 메모리 누수"는 리처 책 시절(Windows XP 이전) 기준. 모던 Windows에선 OS가 스택은 해제함. 하지만 C++ 객체 소멸자가 호출되지 않는 것은 모든 버전에서 동일하며, 그것이 데드락과 누수의 진짜 원인.
💡 책을 보는 시각:
리처 책은 2007년 기준. 모든 내용이 현재 Windows에 100% 맞지는 않음. 책을 읽을 때 "이게 OS 책임인가 컴파일러 책임인가?"를 따지는 사고가 시스템 프로그래머의 핵심 사고방식.

🎯 면접 대비 핵심 암기 사항

  1. 프로세스 = 자원 컨테이너, 스레드 = 실행 주체
  2. 스레드 생성 시 자동 할당: 커널 오브젝트 + 스택(1MB)
  3. CreateThread 매개변수 6개: 보안, 스택 크기, 함수 포인터, 인자, 플래그, ID
  4. 스레드 함수 시그니처: DWORD WINAPI Func(LPVOID)
  5. 종료 방법: return 권장, ExitThread 비권장, TerminateThread 절대 금지
  6. CRT 사용 시 _beginthreadex (또는 std::thread)
  7. 스레드 함수에 스택 변수 주소 넘기지 마라 (race condition)
  8. CloseHandle ≠ 스레드 종료. 핸들과 스레드는 별개 생명주기
  9. 외부에서 스레드 종료: 플래그 + 협력적 종료 패턴
  10. 게임에서는 Thread Pool로 재사용
