섹션 1 · Race Condition · 캐시 라인 · volatile

1-1. 왜 동기화가 필요한가 — Race Condition

겉보기에 atomic처럼 보이는 g_x++는 정말 한 번에 끝나는 작업인가?
핵심 명제: g_x++는 3단계 RMW(Read-Modify-Write)다. x86 어셈블리로 풀면 3개의 명령이고, 그 사이 어디서든 컨텍스트 스위치가 가능하다. 
; g_x++의 실제 어셈블리
MOV  EAX, [g_x]    ; Read  — 메모리 → 레지스터
INC  EAX           ; Modify — 레지스터에서 증가
MOV  [g_x], EAX    ; Write  — 레지스터 → 메모리

전형적인 race 시나리오 (g_x = 5)

시점Thread AThread Bg_x
t1EAX = 5 (Read)—5
t2— (스위치)EAX = 5 (Read)5
t3—EAX = 6 (Inc)5
t4—g_x = 6 (Write)6
t5EAX = 6 (Inc) (복귀)—6
t6g_x = 6 (Write)—6
⚠️ 흔한 오해: "롤백된다"는 표현은 틀림.
다른 스레드의 작업이 취소되는 게 아니라, 늦게 복귀한 스레드가 stale한 값으로 덮어쓰면서 다른 스레드의 증가가 묻혀버리는 것. 정확한 용어는 "lost update".
💡 게임 엔진 맥락: 메인 스레드가 g_frameCount++ 하고 렌더 스레드가 그걸 읽는 패턴. 보호 안 하면 통계 손상, 더블 버퍼링 인덱스 꼬임으로 직결.

1-2. 캐시 라인과 False Sharing

핵심 명제: CPU는 메모리를 바이트 단위가 아니라 캐시 라인 단위(보통 64바이트)로 가져온다. 두 스레드가 다른 변수를 만지더라도, 그 변수들이 같은 캐시 라인에 살면 MESI 코히런시 트래픽이 폭증 = False Sharing.

해결: 캐시 라인 정렬 + 패딩

struct alignas(64) PaddedCounter {
    long value;
    char pad[60];  // 64 - sizeof(long)
};
💡 게임 엔진 맥락: Job system 워커별 카운터를 패딩 안 하면 8코어가 1코어보다 느려질 수 있음. Unreal의 FThreadStats, EASTL의 EASTL_ALIGN_OF가 다 이거 때문.

1-3. volatile — 동기화 도구가 아니다

핵심 명제: volatile은 컴파일러 최적화 방지일 뿐. 원자성/CPU재정렬차단/캐시동기화는 전부 못함.
도구컴파일러 최적화RMW 원자화CPU 재정렬캐시 동기화
volatile✅❌❌❌
InterlockedIncrement✅✅✅✅
std::atomic<long>✅✅✅✅
⚠️ 면접 함정: Java/C#의 volatile은 acquire/release 시맨틱 있음. C/C++의 volatile은 그게 아니다.
⚠️ 흔한 오해: "volatile = RAM에서 직접 읽는다"

volatile은 컴파일러에게 하는 말: "이 값을 레지스터에 박아두고 재사용하지 말고, 매번 load 명령어를 내라."
그 load 명령어가 CPU에 전달된 이후는 volatile이 관여하지 못한다. L1에서 가져올지 RAM에서 가져올지는 CPU 하드웨어가 결정한다.
계층설명
컴파일러가 보는 세계레지스터 | 메모리 (캐시+RAM 통틀어서)
하드웨어 실제 구조레지스터 | L1 | L2 | L3 | RAM
volatile이 바꾸는 것레지스터 재사용 금지 → 매번 load 명령어 생성 (컴파일러 레벨)
volatile이 못 하는 것그 load가 L1에서 오는지 RAM에서 오는지 — CPU가 결정, volatile 무관
정확한 표현: "volatile = 레지스터 재사용 금지". RAM 직접 접근과는 무관.

1-3+. 심화 복습 — "volatile은 캐시 동기화를 못 막는다"의 진짜 의미

📌 이 코너는 복습 중 나온 Q&A를 정리한 것. 하드웨어가 순수하게 어떻게 도는지(volatile/atomic 빼고) → 그래서 volatile이 뭘 못 하는지 순서로 읽으세요.

① 코어가 값을 수정하는 진짜 경로

수정값은 RAM으로 바로 안 감. 레지스터 → store buffer → L1 캐시 → (한참 뒤) RAM 순서. 
// 코어 A가 g_x(=5)를 6으로 증가
R (Read)   : L1 캐시 → 레지스터 (5)        // 캐시에 없으면 RAM서 64B 라인 적재
M (Modify) : 레지스터에서 +1 → 6
W (Write)  : 레지스터 → store buffer → L1     // 이 순간 L1은 아직 5, store buffer만 6
store buffer가 존재하는 이유: 값을 쓰려면 캐시 라인 소유권(RFO, Read For Ownership)이 필요한데, RFO는 버스 타고 다른 코어 무효화시키고 응답 기다리는 느린 작업(수십~수백 사이클). 매번 기다리면 코어가 멈추니까 → 일단 store buffer에 던져놓고 코어는 계속 실행, RFO는 백그라운드로.

② 그래서 다른 코어가 옛값을 보는 "틈"이 생긴다

코어 A: 6을 store buffer에 넣음 ──── RFO 진행 중 ──── L1에 6 commit + B 무효화
                          ↑                            ↑
              [B 캐시 아직 Invalid 아님]        [여기부터 B는 못 봄]
                  B가 이 틈에 자기 캐시의 5를 읽음
store buffer는 코어 A의 사적 공간 — MESI 사정권 밖. 6이 store buffer에 갇혀 L1까지 안 내려간 그 틈에 B가 읽으면 자기 캐시의 옛값(5)을 봄.

③ MESI는 "갱신"이 아니라 "무효화" 프로토콜

오해 (update 방식)실제 MESI (invalidate 방식)
"내 새 값 6으로 너네 캐시 갱신해""너네 사본 그냥 버려(Invalid). 필요하면 나중에 와서 가져가"
흐름: A가 RFO 발사 → B의 g_x 라인 Invalid 처리 → A가 소유권 획득 → store buffer의 6을 L1에 commit, 라인 = Modified(나만 최신, RAM도 모름). RAM은 안 건드림 — eviction 때나 갱신. 나중에 B가 g_x 읽을 때 "내 거 Invalid네" → 버스 요청 → A가 6 넘겨줌(lazy).

무효화 타이밍: "L1 적재되는 순간"이 아니라 그 전제조건으로 직전에 일어남(소유권 따는 행위 = 남 무효화).

④ 메모리 배리어가 하는 일 — store buffer ≠ 배리어 전체

배리어 종류건드리는 큐효과
Store barrierstore buffer 비움(drain)내가 쓴 값이 다른 코어에 보이게
Load barrierinvalidation queue 처리밀린 무효화 신호 즉시 반영 → stale 안 봄
Full barrier둘 다 + 재배치 차단완전 동기화
"store buffer 비우기 = store 배리어가 하는 일"은 맞지만 메모리 배리어 전체 = store buffer 비우기는 아님. 동기화는 양쪽이 짝 맞춰야 함: 쓰는 코어는 store buffer 비우고, 읽는 코어는 invalidation queue 처리. (x86은 메모리 모델이 강해 ARM보다 배리어가 덜 필요)

⑤ ★가장 중요★ 카운터 버그의 진짜 원인은 MESI/store buffer가 아니다

흔한 오해: "두 코어가 백만 번씩 증가시켰는데 2백만이 안 나온 건 캐시 동기화(MESI/store buffer) 때문이다." → 틀림. 진짜 원인은 RMW 비원자성 = lost update(섹션 1-1).
store buffer/MESI 타이밍lost update (RMW)
증상값이 잠깐 늦게 보임증가분이 영구 증발
카운터 버그 원인?❌ 아님✅ 이것
해법메모리 배리어원자적 RMW (LOCK / Interlocked)
결정적 증거 — 싱글 코어에서도 터짐: 캐시 동기화 문제는 코어 2개 이상일 때만 발생(캐시가 여러 개라서). 그런데 lost update는 코어 1개 + 멀티스레드에서도 그대로 발생 — A가 Read → 컨텍스트 스위치 → B가 증가 → A 복귀해 옛값으로 Write. 캐시가 하나뿐이라 MESI/store buffer 이슈가 0인데도 증발. ∴ 캐시 때문이 아님.

또 하나: B가 R 단계에서 읽은 값은 stale이 아니라 그 순간 진짜 최신값이었음. 캐시가 완벽해도 두 코어가 같은 값을 읽는 건 못 막음. lost update는 W가 아니라 R 단계에서 이미 결정됨.
왜 헷갈리나: InterlockedIncrement가 둘 다 고쳐서. LOCK 접두사가 ① RMW 원자화(←카운터를 고치는 실제 부분) ② 메모리 배리어(←가시성 버그도 덤). 카운터를 고친 건 ①이고 ②는 부수 효과.

⑥ "done=true 했는데 다른 스레드가 영영 못 본다"의 진짜 범인 = 컴파일러

하드웨어(store buffer/MESI) 지연은 나노~마이크로초라 "잠깐 늦음"이지 "영영"이 아님. "영영"의 범인은 컴파일러 캐싱. 
// 스레드 B — 컴파일러 눈엔 루프 안에서 done을 아무도 안 바꿈
while (!done) {}        // 원본

// 컴파일러 최적화 결과 — done을 레지스터에 한 번만 읽고 재사용
if (!done) { while(true){} }   // ❌ 메모리 다시 안 읽음 → 영원한 무한 루프
A가 메모리의 done을 true로 바꿔도 B는 메모리를 아예 안 읽으니 영영 모름. 하드웨어가 아무리 빨라도 소용없음(B가 안 읽으니까). → 이건 volatile이 고침("매번 메모리서 다시 읽어라"). 단 volatile은 딱 여기까지, 순서/원자성은 여전히 못 함.

⑦ volatile만으론 동기화 안 되는 예시 — producer/consumer 플래그

volatile bool ready = false;
int data = 0;              // 일부러 volatile 안 붙임 (포인트)

// 생산자
data = 42;            // ① 데이터 먼저
ready = true;         // ② 준비 알림

// 소비자
while (!ready) {}      // ③ 대기
printf("%d\n", data); // ④ 42 나와야 정상 → 근데 0/쓰레기 가능
왜 깨지나: volatile은 ready를 매번 읽긴 하지만 ①과 ② 사이 순서를 보장 안 함. 컴파일러나 CPU가 ②를 ①보다 먼저 내보낼 수 있음(특히 ARM 약한 메모리 모델) → B가 ready=true를 봤는데 data는 아직 0 → 0 출력. C/C++의 volatile은 volatile↔일반변수(data) 순서를 안 지킴. 
// 해법: atomic + acquire/release 배리어
std::atomic<bool> ready{false};
data = 42;
ready.store(true, std::memory_order_release);   // 이전 모든 쓰기를 ready보다 먼저 + 그 순서로 보이게

while (!ready.load(std::memory_order_acquire)) {} // 이후 읽기는 ready 본 다음
printf("%d\n", data); // 항상 42 보장
한 줄 정리: 동기화 = 값 하나 잘 읽기가 아니라 여러 변수 사이의 순서 + 가시성. volatile엔 그게 없다. "volatile로 동기화 되냐 → 아니오"의 정확한 근거.

⑧ A가 RFO 발사하면 B, C는 어떻게 A한테 받을 줄 알까?

답: B, C가 직접 판단 안 함. 그냥 "나 Invalid, 인터커넥트야 줘" 요청만 하면 됨.
누가 최신값을 갖고 있는지 추적하는 건 하드웨어(캐시 코히런시 인터커넥트) 의 역할.

흐름

A: LOCK INC → RFO 발사
    → 인터커넥트가 B, C에게 "g_x 라인 Invalid해" 브로드캐스트
    → B, C: ACK 응답
    → A: ACK 다 받으면 소유권 획득 → 작업 완료 (Modified)

이후 B가 g_x 접근:
    → "내 거 Invalid" → 캐시 미스 → 인터커넥트에 요청
    → 인터커넥트/디렉터리: "A가 Modified로 갖고 있어" → B를 A에 연결
    → A → B로 최신값 전달

하드웨어 구현 방식 두 가지

방식원리적합한 규모
스누핑(Snooping) 모든 코어가 버스 트래픽을 엿들음(snoop). "누가 Modified?" 전체에 물으면 Modified 가진 코어가 응답. 코어 ~8개 이하 (데스크탑 CPU)
디렉터리(Directory) 중앙 테이블이 "g_x는 지금 A가 Modified 소유"를 기록. B가 요청하면 디렉터리가 "A한테 가"라고 안내. 코어 수십~수백 (서버 CPU)
핵심: B, C는 "누구한테 받아야 하냐"를 모른다. 모를 필요도 없다. 하드웨어가 추적하고 연결해주는 것이 캐시 코히런시 인터커넥트의 역할.

1-5. 퀴즈 Q1~Q3 회상

Q1. 1,728,712 같은 애매한 숫자가 나오는 이유는?
나의 답: RMW 어디서든 컨텍스트 스위치 가능. A가 stale 값으로 덮어쓰면서 증가 묻힘. → ✅ 메커니즘 정확, "롤백 아니라 stale write" 자기정정 굳.
보강: 컨텍스트 스위치 시점이 OS 스케줄러에 의해 무작위. 손실 개수가 매 실행마다 달라서 [1M ~ 4M] 분산. 이 재현 불가능성이 race의 signature.
Q2. volatile로 바꾸면 결과가 4,000,000에 가까워지는가?
나의 답: ① 거의 변화 없음 ② 최적화 막기, 매번 메모리 왕복 ③ CPU 재정렬 못 막음 → ①② ✅, ③ 부분 정답.
3가지 층위 (중요도 순):
  1. 원자성 부재 (← 카운터 예제의 직접 원인): volatile은 RMW를 묶지 않음
  2. CPU 메모리 재정렬: out-of-order, store buffer 못 막음 — DCL, lock-free 큐에서 본질적
  3. 캐시 코히런시 지연: store buffer 거치며 시차
Q3. cout << "..." << id << endl;이 카운터 race와 같은 종류인 이유?
나의 답: cout도 문장 전체 출력 전에 컨텍스트 스위치 가능. → ✅ 본질 정확.
구체화: << 호출이 한 줄에 3번. 각 호출 사이 스위치 가능. "여러 단계 작업을 여러 스레드 동시"가 race의 본질 = RMW 3단계와 같은 패턴.

섹션 1 정리

  • Race = RMW 비원자성 + 임의 시점 컨텍스트 스위치
  • 결과의 불규칙성이 race의 signature
  • False Sharing — 데이터 공유 없어도 캐시 라인 공유로 폭락 → alignas(64)
  • volatile은 컴파일러 최적화 방지용 — 원자성/재정렬/캐시 모두 못함
  • C/C++의 volatile ≠ Java/C#의 volatile

섹션 2 · Interlocked 계열

2-1. Interlocked가 작동하는 원리 — LOCK 접두사

락 없이 어떻게 원자성을 만들 수 있을까?
핵심 명제: x86의 LOCK 명령어 접두사가 RMW를 하드웨어 수준에서 단일 트랜잭션으로 묶는다. 락도 커널 진입도 없이 ~10–20 ns에 끝남. 
; InterlockedIncrement(&g_x)가 만들어내는 어셈블리
LOCK INC  dword ptr [g_x]
; ↓ 이 한 명령이:
; 1. 버스/캐시 라인 락 — 다른 코어 접근 차단
; 2. Read-Modify-Write를 단일 트랜잭션으로
; 3. 풀 메모리 배리어 — 재정렬 차단

두 가지 접근의 대조

접근철학예시
(A) 락"내가 끝낼 때까지 다른 스레드 막아"Critical Section (섹션 3)
(B) 원자화"이 작업 자체를 CPU 명령 한 방으로"Interlocked (이번 섹션)
⚠️ 제약: 자연 정렬 필수. LONG(4B)은 4바이트 경계, LONG64는 8바이트 경계. #pragma pack이나 union 안에 박아 정렬 깨지면 silent UB.

2-2. 주요 함수 5가지 — 반환값에 집중하기

① InterlockedIncrement / InterlockedDecrement

LONG InterlockedIncrement(LONG volatile* Addend);
// 효과: ++(*Addend);
// 반환: 증가된 후의 새 값 ← POST-increment
⚠️ C++의 후위 i++(이전 값)과 다름. InterlockedIncrement는 새 값을 반환.

② InterlockedExchangeAdd

LONG InterlockedExchangeAdd(LONG volatile* Addend, LONG Value);
// 효과: *Addend += Value;
// 반환: 더하기 전 이전 값 ← PRE-add
활용: 인덱스/일감 분배 
LONG myIndex = InterlockedExchangeAdd(&g_nextIndex, batchSize);
// myIndex ~ myIndex+batchSize-1 가 내 차지

③ InterlockedExchange

LONG InterlockedExchange(LONG volatile* Target, LONG Value);
// 효과: *Target = Value;
// 반환: 교체 전 이전 값
활용: "처음 세트한 사람이 작업 맡기" 
if (InterlockedExchange(&g_initialized, 1) == 0) {
    // 0 → 1로 바꿔낸 첫 사람만 진입
}

④ InterlockedCompareExchange — lock-free의 왕 (CAS)

LONG InterlockedCompareExchange(
    LONG volatile* Destination,
    LONG Exchange,    // 새로 쓸 값
    LONG Comparand    // 비교 기준
);
// 원자적:
//   if (*Destination == Comparand) { *Destination = Exchange; }
// 반환: *Destination의 이전 값 (성공 = 반환값 == Comparand)
CAS 루프 — 임의 RMW를 lock-free로: 
LONG oldVal, newVal;
do {
    oldVal = g_x;
    newVal = compute(oldVal);
} while (InterlockedCompareExchange(&g_x, newVal, oldVal) != oldVal);
// 읽음 → 계산 → "내가 읽은 그 값 그대로면 바꿈, 아니면 재시도"
⚠️ ABA 문제: A→B→A로 바뀌면 CAS는 "변화 없음"으로 오판. 카운터에선 무관하지만 포인터 기반 자료구조(lock-free 큐/스택)에서 핵심 함정.

⑤ 64-bit / 포인터 버전

InterlockedIncrement64(LONGLONG*);
InterlockedExchangePointer(PVOID*, PVOID);
InterlockedCompareExchangePointer(PVOID*, PVOID, PVOID);

2-5. 퀴즈 Q1~Q2 회상 + CAS 보강

Q1. 4M번의 LOCK을 줄이려면? 캐시 관점에서 왜 더 빠른가?
나의 답: "for문 들어가기 전에 Lock. InterlockedExchange로 0→1 swap, 끝나면 0으로". → 방향 어긋남. 락 기반 직렬화 접근(섹션 3 주제)이고, 단순 Exchange로는 안전한 spin lock도 못 만듦.
의도한 답: 로컬 배칭 + ExchangeAdd 1회 
LONG localCount = 0;
for (int i = 0; i < 1000000; ++i) {
    ++localCount;  // 로컬 변수 — 동기화 불필요
}
InterlockedExchangeAdd(&g_counter, localCount);  // 루프 끝에 1번만
핵심: 각 스레드는 독립적으로 일하고 마지막에만 모임. 병렬성을 유지하면서 LOCK은 4번만.
⚠️ 단순 InterlockedExchange로 spin lock 못 만드는 이유: "이전이 뭐였든 무조건 1로 덮음". 따라서 "if (g_lock == 0) Exchange(1)" 같은 분리된 체크는 사이에 스위치가 끼면 둘 다 진입함. 진짜 안전한 락은 CAS 필요: "이전이 정확히 0일 때만 1로". 이게 Critical Section의 내부 구현.
Q1-3. 캐시 관점에서 왜 더 빠른가?
나의 답: "False Sharing 원인 때문?" → 부분 정답. 비슷한 메커니즘이나 엄밀히 다른 용어.
정확한 용어: True Sharing (캐시 라인 ping-pong)
  • False Sharing: 다른 변수가 같은 라인에 있어 의도치 않게 충돌
  • True Sharing: 진짜 같은 변수를 여러 코어가 만져서 충돌 — 우리 케이스
LOCK INC 1번 = 해당 라인을 다른 3개 코어 캐시에서 invalidate. 백만 번 LOCK = 백만 번 라인 빼앗기. 4번으로 줄이면 ping-pong도 백만 배 감소. 이게 명령어 비용보다 큰 핵심.
Q2. g_counter = g_counter * 2 + 1 같은 복합 연산을 원자적으로?
나의 답: 미답 (다음 학습 포인트로 식별).
왜 ExchangeAdd로 안 되는가: 더할 값이 고정 상수가 아니라 현재 값에 의존(5 → 11, 11 → 23). 모든 가능 연산을 위한 함수는 없음.

해결: CAS 루프 
LONG oldVal, newVal;
do {
    oldVal = g_counter;
    newVal = oldVal * 2 + 1;
} while (InterlockedCompareExchange(&g_counter, newVal, oldVal) != oldVal);
핵심: 읽기-계산은 락 없이, 쓰기만 조건부 원자적. "내가 읽은 사이 누가 안 바꿨다는 가정 하에만 커밋." → 모든 lock-free 자료구조(큐/스택)의 기초.

2-6. CAS 보너스 실습 — MyAtomicAdd 직접 구현

InterlockedExchangeAdd가 없다 가정. InterlockedCompareExchange만으로 동일 기능을 구현하라.

완성된 구현

LONG MyAtomicAdd(LONG volatile* p, LONG value)
{
    LONG oldVal, newVal;
    do {
        oldVal = *p;
        newVal = oldVal + value;
    } while (InterlockedCompareExchange(p, newVal, oldVal) != oldVal);
    return oldVal;
}

// 사용:
for (int i = 0; i < 1000000; ++i) {
    MyAtomicAdd(&g_counter, 1);
}
4스레드 × 1M = 정확히 4,000,000. 10회 검증 통과. 합격

디버그 스토리 — -1 미스터리

실수: MyAtomicAdd(&g_counter, g_counter + 1);
"1을 더하라"가 아니라 "현재 값+1만큼 더하라"가 되어버림 → 매 호출 약 2*g + 1

왜 -1? 0부터 1, 3, 7, 15, ..., 2^n - 1. n=32에서 0xFFFFFFFF = signed LONG의 -1. 한 번 -1 도달하면 2*(-1)+1 = -1로 영원히 고착.

교훈: Q2 강의의 복합 연산 예시(g_counter * 2 + 1)와 보너스 실습 스펙(단순 +1)을 헷갈리지 말 것. CAS 구현 자체는 무결했음.

Q-a 채점: 왜 do-while인가?

나의 답: "do-while 안 쓰면 oldVal/newVal 갱신 안되는 문제" → 부분 정답. 방향은 맞지만 정확하지 않음.
정확한 이유 2가지:
  1. 코드 중복 회피 — while로 쓰면 진입 전 한 번, 실패 시 또 한 번 같은 두 줄을 반복해야 함
  2. "최소 한 번 시도" 의미와 자연스럽게 일치 — CAS 루프의 본질이 "일단 해보고, 실패하면 다시"이므로 do-while이 시맨틱과 정확히 매칭
// while 버전 — 중복
oldVal = *p; newVal = oldVal + value;
while (InterlockedCompareExchange(p, newVal, oldVal) != oldVal) {
    oldVal = *p; newVal = oldVal + value;  // 두 줄 중복
}
💡 고급 트릭: InterlockedCompareExchange는 실패 시 *p의 실제 현재 값을 반환. 그래서 그 반환값을 그대로 다음 oldVal로 쓰면 재읽기 불필요. 
LONG oldVal = *p;
for (;;) {
    LONG newVal = oldVal + value;
    LONG actual = InterlockedCompareExchange(p, newVal, oldVal);
    if (actual == oldVal) return oldVal;  // 성공
    oldVal = actual;  // 실패 시 — 재읽기 없이 반환값 활용
}

Q-c 심화: Lock-free vs Wait-free

나의 답: "매번 실패하면 무한 루프 아닌가요?" → 정답. 추가로 알아둘 보장 단계가 있음.
보장정의우리 CAS 루프
Lock-free시스템 전체가 항상 progress✅ 누군가는 매번 성공
Wait-free모든 개별 스레드가 유한 횟수 안에 성공❌ 이론적으로 한 스레드 starvation 가능
Obstruction-free단독 실행 시 progress✅
⚠️ 신화 깨기: "lock-free = 더 빠르다" 는 거짓.
  • 경합 낮을 때만 빠름. 경합 심하면 CRITICAL_SECTION보다 느려질 수 있음 — CAS 재시도가 캐시 ping-pong 폭증시킴
  • 완화: exponential backoff, x86 _mm_pause() spin hint
  • 게임 엔진도 lock-free 자료구조는 경합 패턴 측정 후 선택

섹션 2 정리

  • Interlocked = 하드웨어 LOCK 접두사로 RMW를 한 트랜잭션화. 락 X, 커널 X, ~10–20 ns
  • Increment(POST 반환), ExchangeAdd(PRE 반환), Exchange(swap), CompareExchange(CAS), 64/포인터 버전
  • 핵심 패턴: 로컬 배칭 + 마지막에 ExchangeAdd 1회 (캐시 ping-pong 최소화)
  • 임의 RMW가 필요하면 CAS 루프(do-while): 읽기-계산-조건부 쓰기-재시도. 실패 시 반환값이 곧 새 current 값
  • 한계: 변수 하나만, 복합 불변식 불가, 자연 정렬 필수 → 그 외엔 다음 섹션의 Critical Section
  • Lock-free ≠ Wait-free. 경합 심하면 락보다 느릴 수도 있음 — 신화 주의

D-1. 가장 단순한 데드락 — ABBA 패턴

두 락이 필요한 작업에서 어떻게 데드락이 만들어지는가? (게임 엔진 시나리오: 메시 캐시 + 텍스처 캐시) 
CRITICAL_SECTION g_meshLock;

// Thread 1: 자산 로더 — 메시 → 텍스처
unsigned __stdcall AssetLoader(void*) {

    ...
}

// Thread 2: 렌더링 — 텍스처 → 메시 (반대 순서!)

Lock Hierarchy — 락이 수십 개일 때

enum LockLevel {
    LOCK_LEVEL_RESOURCE  = 1,  // 메시, 텍스처, 사운드
    LOCK_LEVEL_SCENE     = 2,  // 씬 그래프
    LOCK_LEVEL_RENDER    = 3,  // 렌더 큐
    LOCK_LEVEL_WORLD     = 4,  // 월드 상태
};

// 디버그 빌드에서 assert: 더 높은 레벨만 잡을 수 있음
static thread_local int currentMaxLevel = 0;
void Enter(CRITICAL_SECTION* cs, int level) {
    assert(level > currentMaxLevel);
    EnterCriticalSection(cs);
    currentMaxLevel = level;
}
💡 같은 종류 락 여러 개 (예: 두 메시 락) 사이엔 레벨 차이가 없을 때: 주소 비교로 순서 강제. if (&lockA < &lockB) Enter(A); Enter(B); — 객체 주소가 일관된 순서를 제공.

D-3. 해법 2 — TryEnter + 백오프 (조건 2 깨기)

순서를 강제할 수 없는 경우 (락 정체가 런타임 결정): "하나도 잡을 수 없으면 가진 것까지 다 놓는다" 
while (true) {
    EnterCriticalSection(&g_lockA);
    if (TryEnterCriticalSection(&g_lockB)) {
        // 둘 다 잡음 — 진행
        DoWork();
        LeaveCriticalSection(&g_lockB);
        LeaveCriticalSection(&g_lockA);
        break;
    }
    LeaveCriticalSection(&g_lockA);  // B를 못 잡으면 A도 풀음
    Sleep(0);                          // 또는 _mm_pause()
}
⚠️ 단점:
  • Livelock: 두 스레드가 동시 양보 반복 → 랜덤 백오프로 완화
  • 일감 낭비: 작업 일부 하다 놓으면 무효 → 짧고 idempotent한 작업에만

섹션 3 · Critical Section

3-1. CS는 무엇인가 — 유저 모드 하이브리드 락

Interlocked로 안 되는 경우(변수 2개 이상의 일관된 갱신)는 어떻게?
핵심 명제: CRITICAL_SECTION은 유저 모드 + 커널 모드 하이브리드. 경합 없으면 유저 모드에서 끝(빠름), 경합 길어지면 커널 객체로 대기(비쌈).

EnterCriticalSection의 내부 작동

  1. 첫 시도: InterlockedCompareExchange로 락 상태 0→1. 성공 시 즉시 진입. 커널 진입 없음 (~25ns)
  2. 실패 시 spin: CPU 명령으로 빙빙 돌면서 재시도. spin count(기본 0, 멀티코어 ~4000) 동안 CAS 반복
  3. 그래도 실패: 그제서야 커널의 이벤트 객체로 대기. 컨텍스트 스위치 → 비용 폭증 (수 ㎲ ~ ms)
💡 Mutex vs CS: Mutex는 처음부터 커널 객체 → 무조건 커널 진입. CS는 무경합 시 Mutex보다 100배 빠르고, 경합 심해도 비슷. 같은 프로세스 내 동기화는 거의 항상 CS가 답.

3-2. 4단계 사용법

CRITICAL_SECTION g_cs;

int main() {
    InitializeCriticalSection(&g_cs);
    // 또는 InitializeCriticalSectionAndSpinCount(&g_cs, 4000); ← 멀티코어 권장

    // ... 스레드 생성 ...

    DeleteCriticalSection(&g_cs);
}

void Worker() {
    EnterCriticalSection(&g_cs);
    // shared_data 접근
    LeaveCriticalSection(&g_cs);
}

TryEnter 활용 — 비차단 진입

if (TryEnterCriticalSection(&g_cs)) {
    // 운 좋게 즉시 잡음 — 빠른 경로
    DoWork();
    LeaveCriticalSection(&g_cs);
} else {
    // 다른 스레드가 잡음 — 다른 일 먼저, 나중에 재시도
    DeferWork();
}
게임 엔진: 메인 스레드가 렌더링 중 락 못 잡으면 다음 프레임에 미루는 식.

3-3. 재귀(Recursive) 특성 — Win32 CS는 재귀 락

EnterCriticalSection(&g_cs);  // 카운터 1
EnterCriticalSection(&g_cs);  // 같은 스레드가 또 → 카운터 2 (블록 X)
...
LeaveCriticalSection(&g_cs);  // 카운터 1
LeaveCriticalSection(&g_cs);  // 카운터 0 → 진짜 해제
왜 재귀? 함수 A가 CS 잡고 함수 B 호출, B도 같은 CS 잡으려는 경우 self-deadlock 방지. 단, Enter 횟수 = Leave 횟수 필수.
⚠️ std::mutex는 재귀 아님. 같은 스레드가 두 번 잡으면 데드락. 재귀 필요하면 std::recursive_mutex.

3-5. 미니 실습 — Stats 보호 (sum + count)

두 변수 sum, count를 동시에 갱신. Interlocked로 안 되는 케이스. 
struct Stats {
    LONG sum;
    LONG count;
};
Stats g_stats = { 0, 0 };
CRITICAL_SECTION g_cs;

unsigned __stdcall ThreadProc(void*) {
    for (int i = 0; i < 1000000; ++i) {
        int value = rand() % 100 + 1;     // 락 밖
        EnterCriticalSection(&g_cs);
        g_stats.sum += value;                // 락 안
        g_stats.count++;                     // 락 안
        LeaveCriticalSection(&g_cs);
    }
    return 0;
}
결과 (4스레드 × 1M): count = 4,000,000 / sum ≈ 201,798,976 / avg = 50.
합격

"avg가 항상 50인 이유" — 큰 수의 법칙

rand() % 100 + 1의 이론 평균 = 50.5 (균등분포).
표본 평균 표준 오차 = 28.87 / √4M ≈ 0.0144 → 표본 평균은 [50.486, 50.514] 범위에 99% 확률로 들어감.
정수 나눗셈이 50.45를 50으로 자름. 버그 아니라 수학.

검증: (double)g_stats.sum / g_stats.count 로 출력하면 진짜 평균 50.44~ 가 보임.

Q-b. 두 줄 사이에 Sleep(0)을 끼우면?

  • 정확성은 영향 없음: count = 정확히 4M. 락이 유지되므로 다른 스레드 진입 불가 — 보호 완벽
  • 처리량만 무너짐: 락 점유 시간 폭증 → 다른 3개 스레드 봉쇄 → 4코어가 1코어처럼 직렬화 → 실행 시간 수십~수백 배

왜 잃는가 — 감시 스레드 시나리오

// 다른 스레드에서 평균 모니터링

LONG c = g_stats.count;     // 시점 t2

t1과 t2 사이에 워커가 끼어들어 sum += 75만 하고 count++ 전이라면 → s는 +75 반영, c는 미반영 → 평균이 부풀려짐.

CS 버전에선 감시 스레드도 EnterCriticalSection 잡으니 워커가 두 줄 다 끝낸 일관된 시점에서만 봄.

우리 코드에선 왜 문제 없었나?

"감시 스레드"가 없음. 메인은 WaitForMultipleObjects 뒤에 읽음 → 모든 워커 종료 후 일관 상태. "1초마다 평균 출력하는 스레드"를 추가하는 순간 Interlocked 버전은 깨짐.

섹션 3 정리

  • CS = 유저 모드 하이브리드 락. 무경합 ~25ns, 경합 시 spin 후 커널 대기
  • 4단계: Init/Enter/Leave/Delete (+ TryEnter, AndSpinCount)
  • Win32 CS는 재귀. Enter 횟수 = Leave 횟수 필수
  • 임계 영역 짧게, malloc/IO/Sleep 금지, RAII로 Leave 보장
  • CS의 진짜 존재 이유: 복합 불변식. 두 변수의 동시 일관성이 필요할 때 Interlocked로는 불가
  • 다중 락 시 lock ordering으로 데드락 방지 (위 데드락 코너 참조)

섹션 4 · SRWLOCK — Slim Reader-Writer Lock

4-1. 왜 SRWLOCK이 필요한가

CS의 약점: 모든 스레드를 동등하게 직렬화. 읽기만 하는 100개 스레드도 한 번에 1개만 들여보냄. 읽기는 RMW가 아니라 동시에 해도 데이터 손상 없는데 비효율적. 
// CS 방식 — 읽기만 해도 직렬화
EnterCriticalSection(&g_cs);
int v = g_config.value;
LeaveCriticalSection(&g_cs);

SRWLOCK의 핵심 아이디어

"읽기는 여러 명 동시에, 쓰기는 단독으로."
시점상황허용
T1Reader A, B, C 진입✅ 동시 진입
T2Writer X 진입 시도A,B,C 끝날 때까지 대기
T3Writer X 단독 작업✅ 단독 진입
T4Reader들 재진입✅ 다시 동시
쓰기 대기 중이면 새 읽기 요청도 대기 — Reader starvation 방지.

4-2. 사용법 — 함수 6개

SRWLOCK g_lock;
InitializeSRWLock(&g_lock);   // Delete 함수 없음 — 자동 정리

// 쓰기 (exclusive)
AcquireSRWLockExclusive(&g_lock);
g_config.value = newValue;
ReleaseSRWLockExclusive(&g_lock);

// 읽기 (shared)
AcquireSRWLockShared(&g_lock);
int v = g_config.value;
ReleaseSRWLockShared(&g_lock);

// 비차단 변형 (실패 시 즉시 반환)
TryAcquireSRWLockExclusive(&g_lock);
TryAcquireSRWLockShared(&g_lock);

4-3. CS vs SRWLOCK 비교

현대 Windows 코드의 디폴트는 SRWLOCK. "재귀 안 쓰는 한 SRWLOCK 우선." std::shared_mutex가 내부적으로 SRWLOCK을 씁니다.
선택 기준:
  • 읽기 >> 쓰기 (9:1 이상) → SRWLOCK 압승
  • 읽기 ≈ 쓰기 위주 → 비슷하거나 소폭 SRWLOCK 우세
  • 재귀 호출 필요 → CS만 가능

4-4. 절대 금지 — 읽기 락 → 쓰기 락 업그레이드

// ❌ 데드락 — 절대 금지
AcquireSRWLockShared(&g_lock);
int v = g_config.value;
if (v == 0) {
    AcquireSRWLockExclusive(&g_lock);  // 자기 자신과 self-deadlock
    g_config.value = 1;
    ReleaseSRWLockExclusive(&g_lock);
}
ReleaseSRWLockShared(&g_lock);
같은 스레드가 읽기 락을 잡은 채로 쓰기 락 요청 → SRWLOCK은 "현재 읽기 락 보유자가 다 나갈 때까지" 대기 → 자기 자신이 읽기 락을 들고 있으니 영원히 대기 = self-deadlock.

올바른 패턴 — 놓고, 다시 잡고, 재검사

// ✅ 올바른 패턴
AcquireSRWLockShared(&g_lock);
int v = g_config.value;
ReleaseSRWLockShared(&g_lock);          // 먼저 놓고

if (v == 0) {
    AcquireSRWLockExclusive(&g_lock);
    if (g_config.value == 0) {          // 재검사 필수 — 사이에 다른 스레드가 바꿨을 수 있음
        g_config.value = 1;
    }
    ReleaseSRWLockExclusive(&g_lock);
}
이 "놓고 → 다시 잡고 → 재검사" 패턴은 동시성 라이브러리 디자인의 단골. Double-Checked Locking의 사촌.

4-6. 미니 실습 — 자산 핸들 테이블

시나리오: Writer 1개(로딩, Sleep(10) × 100회) + Reader 9개(매 iter lookup). Writer 완료 후 Reader 종료. 
SRWLOCK g_lock;
map<int, string> g_assets;
LONG g_writerDone = 0;
LONG g_successCount = 0;

unsigned __stdcall WriterThreadProc(void*) {
    for (int i = 0; i < 100; ++i) {
        int id = rand() % 100 + 1;
        AcquireSRWLockExclusive(&g_lock);
        g_assets.insert(make_pair(id, to_string(id)));
        ReleaseSRWLockExclusive(&g_lock);
        Sleep(10);                          // 락 밖에서 Sleep
    }
    InterlockedExchange(&g_writerDone, 1);  // 루프 끝난 후
    return 0;
}

unsigned __stdcall ReaderThreadProc(void*) {
    while (g_writerDone == 0) {
        int id = rand() % 100 + 1;
        AcquireSRWLockShared(&g_lock);
        auto iter = g_assets.find(id);
        ReleaseSRWLockShared(&g_lock);
        if (iter != g_assets.end())
            InterlockedIncrement(&g_successCount);  // 락 밖에서
    }
    return 0;
}
결과: 총 데이터 수 ~65 / 성공 횟수 ~410만
데이터 수 ~65: 100회 삽입, ID 1~100 중복 무시 → 수학적 기댓값 ~63개. 정상.
성공 횟수 410만: Writer Sleep(10)×100 = 약 1초 동안 Reader 9개가 락 경합 거의 없이 풀 스피드. SRWLOCK shared 동시성이 그대로 보임.

초기 작성 시 발생한 버그 2개

버그 1 (치명적): InterlockedExchange(&g_writerDone, 1)을 for 루프 안 + 락 안에 넣음 → i=0 첫 반복에서 바로 writerDone=1 → Reader들 즉시 탈출 → successCount 8~9.

버그 2 (설계): Sleep(10)을 Exclusive 락 안에 넣음 → 10ms 동안 Reader 9개 전부 블로킹 → SRWLOCK 존재 의미 소멸.

공통 교훈: "임계 영역 짧게, Sleep/IO 금지"는 SRWLOCK에서도 동일하게 적용. 개념을 알아도 코드 짤 때 적용이 한 박자 늦어지는 전형적 패턴.

4-7. 퀴즈 Q-a/b/c

Q-a. Writer가 매우 잦아지면(100번 → 10,000번 + Sleep(0)) SRWLOCK이 CS보다 빠를까?
나의 답: 모르겠다
아니오, 오히려 CS보다 느릴 수 있음. Writer가 Exclusive를 자주 잡으면 Reader들이 결국 직렬화 → SRWLOCK의 "공유 읽기" 이점 소멸. 게다가 SRWLOCK은 내부적으로 Reader 수를 카운팅해 CS보다 상태 관리가 복잡 → 오버헤드가 손익분기를 넘어 CS보다 느려질 수 있음.

SRWLOCK은 read >> write일 때만 압승. Write 비율이 높아질수록 CS와 비슷해지거나 뒤집힘.
Q-b. Reader 락 안에서 실수로 g_assets[id] = name처럼 쓰기를 하면?
나의 답: 크래시. operator[]는 없는 키면 삽입+생성. 여러 Reader가 동시에 트리를 수정하면 재할당/크래시. → 정답
보강: map은 red-black tree. operator[]는 non-const — 키 없으면 노드 삽입 + 트리 rebalance. 여러 Reader가 shared 락으로 동시에 트리를 순회하는 중에 한 명이 트리 구조를 변경 → data race → UB → crash. "재할당"보다 정확히는 트리 재구성 중 포인터를 동시에 읽어서 터지는 것.
Q-c. SRWLOCK이 재귀를 지원하지 않는 이유?
나의 답: 모르겠다
SRWLOCK 내부는 8바이트 정수 1개. Reader 수, Writer 대기 여부 등을 비트 필드로 인코딩. 소유한 스레드 ID를 저장할 공간이 없음.

CS는 소유 스레드 ID를 별도 필드에 기록 → "같은 스레드가 다시 들어왔네" 감지 가능. SRWLOCK은 그걸 의도적으로 넣지 않아 8바이트 유지. 크기와 단순성을 위한 의도적 트레이드오프.

섹션 4 정리

  • SRWLOCK = "읽기는 동시에, 쓰기는 단독으로" — CS의 읽기 직렬화 약점 해결
  • 함수 6개, 8바이트, Delete 불필요. 무경합 ~15ns (CS보다 빠름)
  • 재귀 불가 — 소유 스레드 ID 저장 공간 없음 (의도적 설계)
  • shared → exclusive 업그레이드 절대 금지 — self-deadlock
  • 올바른 패턴: 읽기 락 놓고 → 다시 쓰기 락 잡고 → 재검사
  • read >> write 비율일 때만 SRWLOCK 압승. Write 잦아지면 CS와 비슷하거나 역전
  • 임계 영역 짧게 + Sleep/IO 락 밖 — CS와 동일한 규칙 적용

섹션 5 · Condition Variable — 조건 변수

5-1. 왜 Condition Variable이 필요한가

CS/SRWLOCK의 공통 한계: "조건이 충족될 때까지 기다리기"를 효율적으로 못 함. 
// 나쁜 방법 — Busy-waiting: CPU 100% 낭비
while (queue.empty()) { }

// Sleep 끼워도 근본 해결 아님 — 1ms마다 깨어나 확인하는 낭비
while (queue.empty()) { Sleep(1); }
원하는 동작: "조건이 안 됐으면 잠들어 있다가, 조건이 바뀌면 그때 깨워줘."
Condition Variable이 이걸 합니다.
세 가지 요소가 항상 세트:
  1. 락(CS 또는 SRWLOCK) — 조건을 보호
  2. 조건 변수 — 잠들고/깨어나는 신호
  3. 조건 자체 — 내가 기다리는 상태 (!queue.empty() 같은 것)

5-2. API

CONDITION_VARIABLE g_cv;
InitializeConditionVariable(&g_cv);   // Delete 없음

// 잠들기 — CS 버전 (락을 원자적으로 놓고 잠듦)
SleepConditionVariableCS(&g_cv, &g_cs, INFINITE);

// 잠들기 — SRWLOCK 버전
SleepConditionVariableSRW(&g_cv, &g_lock, INFINITE, 0);                               // exclusive
SleepConditionVariableSRW(&g_cv, &g_lock, INFINITE, CONDITION_VARIABLE_LOCKMODE_SHARED); // shared

// 깨우기
WakeConditionVariable(&g_cv);     // 대기 중인 스레드 1개
WakeAllConditionVariable(&g_cv);  // 대기 중인 모든 스레드

SleepConditionVariable의 핵심 동작

SleepConditionVariableCS는 락을 원자적으로 놓고 잠듭니다. 그냥 Sleep()과 다른 이유. 깨어나면 자동으로 락을 다시 잡고 돌아옴.

"락 잡은 채로 자면 Producer가 어떻게 락을 잡냐?" → Sleep이 락을 놓고 자기 때문에 가능. 
Worker: EnterCriticalSection    // 락 잡음
Worker: SleepConditionVariableCS // 락 놓고 + 잠듦 (원자적)
                  ↑ 이 틈에 Main이 락 잡고 push 가능
Main:   EnterCriticalSection → push → LeaveCriticalSection
Main:   WakeConditionVariable   // Worker 깨움
Worker: 깨어남 + 락 자동 재획득 → while 조건 재확인

5-3. 반드시 while 루프 — Spurious Wakeup

허위 깨어남(spurious wakeup): 아무도 깨우지 않았는데 스레드가 깨어날 수 있음. OS/하드웨어 수준의 특성으로 피할 수 없음. 
// ❌ if 쓰면 안 됨 — spurious wakeup 시 queue가 여전히 비어있을 수 있음
if (queue.empty()) {
    SleepConditionVariableCS(&g_cv, &g_cs, INFINITE);
}
queue.front(); queue.pop();  // ← 빈 큐에서 접근 → crash

// ✅ while 써야 함 — 깨어날 때마다 조건 재확인
while (queue.empty()) {
    SleepConditionVariableCS(&g_cv, &g_cs, INFINITE);
}
queue.front(); queue.pop();  // 여기 오면 반드시 데이터 있음
규칙: Condition Variable 대기는 항상 while 루프.

while 탈출 조건 — ||와 &&의 함정

while은 조건이 false가 되는 순간 탈출. 드모르간 법칙으로 따져야 함.
조건탈출하려면결과
while (A || B) A도 false AND B도 false여야 탈출 ❌ 둘 다 false여야 → 탈출 어려움
while (A && B) A false OR B false면 탈출 ✅ 하나만 false여도 → 탈출 쉬움
실수 사례: while (g_jobs.empty() || !g_shutdown) → 탈출하려면 "큐에 뭔가 있음 AND shutdown=true" 둘 다 동시에 만족해야 함. job이 들어와도 shutdown 전이면 탈출 불가 → 영원히 hang.

올바른 코드: while (g_jobs.empty() && !g_shutdown) → 큐에 뭔가 있거나 OR shutdown이면 탈출.

5-6. 미니 실습 — Job Queue

CRITICAL_SECTION g_cs;
CONDITION_VARIABLE g_cv;
queue<int> g_jobs;
bool g_shutdown = false;
LONG g_processedCount = 0;

unsigned __stdcall WorkerThreadProc(void*) {
    while (true) {
        EnterCriticalSection(&g_cs);
        while (g_jobs.empty() && !g_shutdown) {    // &&: 하나만 false여도 탈출
            SleepConditionVariableCS(&g_cv, &g_cs, INFINITE);
        }
        if (g_jobs.empty()) {                       // shutdown + 큐 비어있음 = 종료
            LeaveCriticalSection(&g_cs);
            break;
        }
        g_jobs.pop();
        LeaveCriticalSection(&g_cs);
        InterlockedIncrement(&g_processedCount);  // 처리는 락 밖
    }
    return 0;
}

// Main: 1~1000 push → shutdown + WakeAll
for (int i = 0; i < 1000; ++i) {
    EnterCriticalSection(&g_cs);
    g_jobs.push(i + 1);
    LeaveCriticalSection(&g_cs);
    WakeConditionVariable(&g_cv);
}
g_shutdown = true;
WakeAllConditionVariable(&g_cv);   // 잠든 Worker들 깨워서 종료 처리
결과: g_processedCount = 1000 (1~1000 전부 처리)

발생한 버그 2개

버그 1 — 내부 while 조건에 || 사용:
while (g_jobs.empty() || !g_shutdown) → 탈출 조건이 "큐 비지 않음 AND shutdown=true" 둘 다 동시에 만족해야 함. job이 들어와도 shutdown 전이면 탈출 불가 → 영원히 hang.

버그 2 — g_shutdown=true 후 WakeAll 없음 (1차 코드):
Worker들이 잠든 채로 아무도 안 깨움 → WaitForMultipleObjects에서 Main 영원히 대기 → hang.

5-7. 퀴즈 Q-a/b/c

Q-a. WakeConditionVariable → WakeAllConditionVariable로 바꾸면?
나의 답: 결과 동일, 성능 저하 → 정답
processedCount = 1000으로 동일. 단 매 push마다 Worker 4개가 전부 깨어나 락 경합 후 1개만 처리, 나머지 3개는 다시 잠듦 = Thundering herd. 불필요한 컨텍스트 스위치 × 3배.
Q-b. while 대신 if를 쓰면?
나의 답: Spurious wakeup 대비 불가, crash → 정답
Spurious wakeup 시 큐가 비어있는데 if면 그냥 통과 → pop() 시도 → 빈 큐 접근 → UB → crash.
Q-c. g_shutdown=true 후 WakeAllConditionVariable 안 부르면?
나의 답: 모르겠다 → 버그 2번이 바로 이 케이스
Worker들이 내부 while에서 잠든 채로 아무도 안 깨워줌 → shutdown 신호를 영영 못 봄 → WaitForMultipleObjects에서 Main 영원히 대기 = hang. WakeAll이 "종료 신호를 잠든 스레드들에게 전달하는" 역할.

섹션 5 정리

  • CV = "조건 안 되면 잠들고, 조건 바뀌면 깨워줘" — Busy-waiting 제거
  • 락 + 조건변수 + 조건 세 가지가 항상 세트
  • SleepConditionVariable = 락을 원자적으로 놓고 잠듦. 깨어나면 자동 재획득
  • 대기는 항상 while — Spurious wakeup 방어
  • while 안 || vs && : while은 false에서 탈출. ||는 둘 다 false여야, &&는 하나만 false여도 탈출
  • Wake = 1개, WakeAll = 전체. 종료 신호는 WakeAll
  • shutdown 후 반드시 WakeAll — 잠든 스레드들이 신호를 받아야 종료 가능
