섹션 1 · 왜 커널 객체인가

1-1. 유저 모드 동기화의 한계

핵심 명제: CS·SRWLOCK·CV·Interlocked 는 프로그래머가 명시적으로 신호를 보내야만 동작한다. OS 이벤트(스레드 종료, 프로세스 종료 등)와 자동으로 연동되지 않는다.
필요한 상황유저 모드로 가능?이유
스레드 A가 종료될 때까지 대기❌ 완전 불가스레드 크래시·강제 종료 시 notify 안 됨
프로세스 간 동기화❌유저 모드 객체는 프로세스 경계 못 넘음
타임아웃 포함 대기△ 번거로움CV는 별도 계산 필요
여러 객체 중 하나만 기다리기❌없음
CV로 "스레드 종료 대기"를 흉내낼 때 어디서 깨지나?
스레드 함수 마지막에 notify_all()을 넣어도 — 스레드가 예외·크래시·TerminateThread로 죽으면 notify_all()에 도달하지 못한다. 대기 스레드가 영원히 블로킹. OS가 이 사실을 CV에게 알려줄 방법이 없다.
커널 객체의 해법: Thread HANDLE은 커널 객체다. 스레드가 어떤 이유로든 종료되는 순간 OS가 자동으로 signaled 상태로 전환한다. 크래시·정상 리턴·TerminateThread 모두 포함. 
WaitForSingleObject(hThread, INFINITE); // 종료 방법 무관, 100% 보장

커널 객체란?

OS가 커널 메모리에 할당하고 관리하는 오브젝트. HANDLE로 접근한다. 스레드, 프로세스, 뮤텍스, 세마포어, 이벤트, 타이머, 파일 등이 모두 커널 객체다. 프로세스 경계를 넘어 공유 가능하고, 타임아웃 있는 대기가 가능하다.

핵심 개념: Signaled / Non-signaled

모든 커널 객체는 항상 두 상태 중 하나다.

Signaled — "사용 가능" 또는 "이벤트 발생". Wait 함수를 통과한다.
Non-signaled — "아직 아님". Wait 함수가 스레드를 블로킹한다.

섹션 2 · Wait 함수

2-1. WaitForSingleObject / WaitForMultipleObjects

DWORD WaitForSingleObject(HANDLE hObject, DWORD dwMilliseconds);
DWORD WaitForMultipleObjects(DWORD nCount, const HANDLE* ph,
                             BOOL bWaitAll, DWORD dwMilliseconds);
이 함수를 호출한 스레드는 커널이 대기 상태(suspended)로 전환한다. CPU를 소비하지 않는다. 객체가 signaled되면 커널이 스레드를 깨운다.

반환값

반환값의미
WAIT_OBJECT_0정상 signaled (또는 복수 인덱스: WAIT_OBJECT_0 + i)
WAIT_TIMEOUT타임아웃 만료 — 객체는 아직 non-signaled
WAIT_ABANDONED뮤텍스 소유 스레드가 비정상 종료 (뮤텍스 한정)
WAIT_FAILED함수 오류 — GetLastError()로 원인 확인

dwMilliseconds 특수값

값동작
INFINITEsignaled될 때까지 영원히 대기
0현재 상태만 확인하고 즉시 반환 (논블로킹 폴링)

WaitForMultipleObjects — bWaitAll

bWaitAll = TRUE — 배열의 모든 핸들이 signaled일 때 반환
bWaitAll = FALSE — 배열 중 하나라도 signaled면 즉시 반환. 반환값 WAIT_OBJECT_0 + i가 그 인덱스.
⚠️ bWaitAll = TRUE 주의: 전부 다 signaled가 되는 그 순간을 원자적으로 감지하는 것이 아니다. 하나씩 획득하는 과정에서 데드락이 생길 수 있다. 락 순서와 동일한 주의가 필요하다.

섹션 3 · 커널 객체별 신호 규칙

객체 Signaled 조건 Non-signaled 조건 소유권
프로세스 종료됨 실행 중 없음
스레드 종료됨 실행 중 없음
Mutex 아무도 소유 안 함 누군가 소유 중 있음 (획득 스레드만 해제 가능)
Semaphore 카운트 > 0 카운트 = 0 없음
Event (auto-reset) SetEvent 후 / Wait 성공 즉시 reset 기본 또는 Wait 성공 후 없음
Event (manual-reset) SetEvent 후 — 유지 ResetEvent 호출 후 없음
Waitable Timer 지정 시각 도달 / 주기 경과 타이머 설정 전 / 다음 주기 전 없음

섹션 4 · Mutex

4-1. API

HANDLE CreateMutex(
    LPSECURITY_ATTRIBUTES lpAttr,
    BOOL bInitialOwner,   // TRUE면 생성 즉시 이 스레드가 소유
    LPCTSTR lpName        // NULL이면 익명, 이름 지정 시 프로세스 간 공유
);
BOOL ReleaseMutex(HANDLE hMutex);
WaitForSingleObject로 획득, ReleaseMutex로 해제. 획득한 스레드만 해제 가능하다는 소유권 개념이 있다.

4-2. Mutex의 특성

① 재귀 획득 가능

같은 스레드가 이미 소유 중인 Mutex를 다시 Wait해도 블로킹되지 않는다. 내부적으로 획득 횟수를 카운팅하고, ReleaseMutex를 같은 횟수만큼 호출해야 완전히 해제된다. Critical Section과 같은 동작.

② WAIT_ABANDONED — 소유 스레드 비정상 종료

뮤텍스의 핵심 차별점. 소유 스레드가 ReleaseMutex 없이 죽으면 OS가 자동으로 뮤텍스를 signaled로 전환하고, 대기 중이던 다음 스레드에게 소유권을 넘긴다. 단 반환값이 WAIT_OBJECT_0이 아니라 WAIT_ABANDONED다.

이 값은 "공유 자원 상태가 오염됐을 수 있다"는 경고다. 받았다면 데이터 무결성 검사를 해야 한다.
Critical Section 소유 스레드가 죽으면 어떻게 되나?
CS는 커널 객체가 아니다. OS가 CS 소유자의 생사를 알지 못한다. 락이 영원히 잠긴 채 남아 영구 블로킹이 된다. WAIT_ABANDONED 같은 복구 경로가 없다.

4-3. CS vs Mutex 선택

Critical SectionMutex
종류유저 모드 객체커널 객체
속도 (무경합)~25–50 ns~1,000+ ns (커널 진입)
프로세스 간 공유❌✅ (이름 지정)
타임아웃 대기❌ (TryEnter만)✅
소유자 죽음 복구❌ 영구 블로킹✅ WAIT_ABANDONED
재귀 획득✅✅
선택 기준: 같은 프로세스 내 → CS가 훨씬 빠름. 프로세스 간 공유·타임아웃·소유자 크래시 복구가 필요할 때만 Mutex.

섹션 5 · Semaphore

5-1. API

HANDLE CreateSemaphore(
    LPSECURITY_ATTRIBUTES lpAttr,
    LONG lInitialCount,   // 초기 카운트
    LONG lMaximumCount,   // 최대 카운트
    LPCTSTR lpName
);
BOOL ReleaseSemaphore(
    HANDLE hSemaphore,
    LONG lReleaseCount,       // 카운트를 얼마나 증가시킬지
    LPLONG lpPreviousCount    // 이전 카운트 받을 포인터 (필요 없으면 NULL)
);

5-2. 동작 규칙

카운트 > 0이면 signaled. WaitForSingleObject 성공 시마다 카운트 -1. 카운트가 0이 되면 non-signaled → 이후 Wait 호출 스레드는 블로킹.

소유권 없음. 어느 스레드든 ReleaseSemaphore 호출 가능.

5-3. Mutex vs Semaphore

MutexSemaphore (최대 1)
소유권있음 — 획득 스레드만 해제없음 — 누구나 Release
재귀 획득✅ 같은 스레드 재진입 가능❌ 자기 자신도 블로킹
크래시 복구✅ WAIT_ABANDONED❌
용도공유 자원 상호 배제동시 접근 개수 제한
💡 게임 엔진 예: 동시에 최대 4개 스레드만 asset streaming I/O를 사용할 수 있게 제한. 
// 최대 4개 동시 I/O 허용
HANDLE hSem = CreateSemaphore(NULL, 4, 4, NULL);

// 각 워커 스레드
WaitForSingleObject(hSem, INFINITE);  // 슬롯 획득
DoStreamingIO();
ReleaseSemaphore(hSem, 1, NULL);      // 슬롯 반환

섹션 6 · Event

6-1. API

HANDLE CreateEvent(
    LPSECURITY_ATTRIBUTES lpAttr,
    BOOL bManualReset,    // TRUE = Manual-reset, FALSE = Auto-reset
    BOOL bInitialState,   // TRUE = 처음부터 signaled
    LPCTSTR lpName
);
BOOL SetEvent(HANDLE hEvent);    // signaled로 전환
BOOL ResetEvent(HANDLE hEvent);  // non-signaled로 전환
// BOOL PulseEvent(HANDLE hEvent); — 절대 사용 금지

6-2. Event의 목적 — "자원 보호"가 아니라 "신호 전달"

Mutex·Semaphore는 자원 접근을 제어하는 도구다. Event는 다르다 — "지금 해도 돼"라는 신호를 보내는 도구다. 특정 조건이 충족됐음을 다른 스레드에게 알리는 것이 목적이다. 
// 스레드 A: 맵 로딩
LoadMap();
SetEvent(hMapReady);    // "로딩 끝났어"

// 스레드 B: 렌더러
WaitForSingleObject(hMapReady, INFINITE);  // 로딩 끝날 때까지 CPU 소비 없이 대기
StartRendering();

6-3. Auto-reset vs Manual-reset

Auto-resetManual-reset
SetEvent 후 대기 스레드 하나만 깨움, 즉시 non-signaled로 reset 대기 중인 스레드 전원 깨움, signaled 상태 유지
Reset 시점 Wait 성공한 순간 자동 ResetEvent 명시적 호출 시
이후 도착 스레드 블로킹 (이미 reset됨) ResetEvent 전까지 즉시 통과
게임 엔진 비유 Job queue — 일감 하나에 워커 하나 배정 로딩 완료 브로드캐스트 — 모든 스레드 동시 출발
Manual-reset 사용 이유: "이 조건은 이제 영구적으로 충족됐다"는 상태를 표현할 때. SetEvent 한 번으로 지금 대기 중인 스레드 전부 + 이후 도착하는 스레드까지 통과시킨다. Auto-reset으로 같은 효과를 내려면 스레드 수만큼 SetEvent를 호출해야 하는데, 스레드 수가 가변적이라면 불가능하다.

6-4. PulseEvent — 절대 쓰지 말 것

PulseEvent는 "잠깐 signaled 됐다가 non-signaled로"인데, Wait 직전에 Pulse가 오면 아무도 못 받는 레이스가 있다. 대기 스레드가 커널에 등록되기 전에 Pulse가 지나가면 신호 유실. Windows 공식 문서도 "unreliable"이라고 명시. 사용 금지.

6-5. CV와의 비교

섹션 7 · Waitable Timer

7-1. API

HANDLE CreateWaitableTimer(
    LPSECURITY_ATTRIBUTES lpAttr,
    BOOL bManualReset,   // Event의 Manual/Auto와 같은 개념
    LPCTSTR lpName
);
BOOL SetWaitableTimer(
    HANDLE hTimer,
    const LARGE_INTEGER* pDueTime,  // 음수 = 상대 시간(100ns 단위), 양수 = 절대 시각
    LONG lPeriod,                   // 0 = 1회, >0 = 주기(ms 단위)
    PTIMERAPCROUTINE pfnCompletionRoutine,  // APC 콜백, 필요 없으면 NULL
    LPVOID lpArgToCompletionRoutine,
    BOOL fResume                    // 절전 모드 해제 여부
);
특정 시각 또는 주기로 자동 signaled 된다. lPeriod > 0이면 반복 타이머.

pDueTime 설정 예시

// 5초 후 1회
LARGE_INTEGER li;
li.QuadPart = -(LONGLONG)5 * 10000000;  // -5초 (100ns 단위, 음수 = 상대)
SetWaitableTimer(hTimer, &li, 0, NULL, NULL, FALSE);

// 1초마다 반복
li.QuadPart = -10000000;              // 1초 후 첫 발화
SetWaitableTimer(hTimer, &li, 1000, NULL, NULL, FALSE); // 이후 1000ms 주기
💡 게임 엔진 활용: 특정 주기 작업(프로파일링 샘플링, 네트워크 heartbeat), 타임아웃 구현. 단, 게임 루프처럼 고빈도 정밀 타이밍에는 부적합 — OS 스케줄러 오차가 있다.

챕터 9 정리

  • 커널 객체 = HANDLE + signaled/non-signaled 상태. OS가 상태를 자동 관리
  • 유저 모드의 한계를 넘는 세 가지: 프로세스 간 공유, 타임아웃, OS 이벤트 자동 연동
  • Mutex: 소유권 있음. 소유자 크래시 → WAIT_ABANDONED로 복구 가능. 재귀 획득 OK
  • Semaphore: 소유권 없음. 동시 접근 N개 제한. 누구나 Release
  • Event Auto-reset: 하나만 통과시키고 즉시 reset → Job 분배
  • Event Manual-reset: SetEvent 후 전원 통과, ResetEvent 전까지 유지 → 브로드캐스트
  • PulseEvent: 신호 유실 레이스 있음 — 사용 금지
  • 같은 프로세스 내 고빈도 락은 CS가 Mutex보다 ~20x 빠름. 커널 진입이 없어서
